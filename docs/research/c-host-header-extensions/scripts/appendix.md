# C-mode host header extension inventory: generated appendix

Generated by `scripts/report.py` from the data described in [../c-host-header-extensions.md](../c-host-header-extensions.md) (sections 0 to 2). Do not edit by hand; edit `scripts/appendix.md` or `scripts/classes.py` and regenerate. The same rows are in `data/inventory.tsv`.

Paths are shortened: `aarch64/` is `/usr/include/aarch64-linux-gnu/`, `gcc/` is `/usr/lib/gcc/aarch64-linux-gnu/15/include/`, anything else is under `/usr/include/`.

Columns:
- *Origin*: the package whose header text holds the construct where header code reaches it (for "macro only" names, where the macro is defined): `glibc` (libc6-dev), `kernel` (linux-libc-dev), `gcc` (GCC's own include directory, which Forge replaces with its own headers).
- *Reach*: "code" means the construct is written in header text that GCC emitted; "via macro" means it came from a macro that header code expanded; "macro only" means it sits in a `#define` that GCC processed but no header expanded (live only if user code uses the macro). Configuration sets are written compactly: `gnu17` means both `gnu17` and `gnu17+gs`; `gnu17+gs` means only with `-D_GNU_SOURCE`; "(no gs)" means only without it.
- *Roots per configuration*: for 89, 89g, 99, 99g, 17, 17g, 23, 23g, the number of roots whose TU reaches the name, `m` when it is macro only there, `-` when absent.
- *Forms*: the commonest spellings with arguments.
- *GCC kind*: for identifiers, what gcc-15 itself says the name is (data/../gccnames step).
- *Class reason*: "#9's class" when the class is inherited unchanged.
