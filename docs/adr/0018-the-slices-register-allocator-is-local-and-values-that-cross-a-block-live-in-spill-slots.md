# The slice's register allocator is local, and values that cross a block live in spill slots

The slice has one register allocator, with the shape of clang's at `-O0`. A value that crosses a block boundary (a parameter of any block but the entry, or a value used outside the block that defines it) has a spill slot: it is stored once, right after its def, and reloaded in each other block that uses it, so no register carries a value from one block into another. Each block is then allocated on its own by one walk from its terminator up to its first instruction, as LLVM's fast allocator (clang `-O0`'s) and regalloc2's fastalloc do. Walking up, a value is first met at its last use, a fixed register below a def is met before the def, and by the time the walk reaches a def it knows whether the value was evicted below it. A value live across a `bl` is spilled around it, so the slice never uses the callee-saved registers `x19`–`x28`. Nothing is coalesced: a value takes its use's fixed register, then its def's, then the first free one. The allocator therefore needs no liveness across blocks, no register state at merges and no hints across edges. The map rules the compile-speed and code-quality targets out of scope, and the driver ignores `-O`, so every compile gets this allocator. An allocator chosen by `-O` level, with a forward greedy one for `-O1` and above, is the planned successor: it reads `ssa` and writes `allocated` like this one, and the same checker checks it.

## Considered Options

- **Forward greedy over the layout with liveness across blocks** (V8's Maglev, TPDE), which the compiler-construction research recommended. Values stay in registers across blocks: a block inherits the register state of the first predecessor allocated before it, and every other edge gets a parallel move to match. `sum`'s loop would touch no memory. But it needs liveness across blocks, a state at every merge, a fresh state for a block whose predecessors all come later in the layout (the code after a backward `goto`), hints across edges and the callee-saved registers. It is the planned successor for `-O1` and above.
- **Linear scan on SSA** (Wimmer and Franz): live intervals with holes, splitting and a resolution phase. The code is better again, and there is much more of it. MIR stays SSA until allocation so that either can replace this one (ADR 0008).
- **Callee-saved registers for values live across a call** (clang `-O1`'s `mov x19, x0` before `bl _h`). Each such value saves a store and a reload, but frame lowering has to save the registers, and in a local allocator they would only help within one block.
- **Walking each block top-down.** It needs a pre-walk to find last uses and a table of fixed-register hints, which walking up gets for free.

## Consequences

- Every value that crosses a block goes through memory: `sum`'s loop loads and stores both of its variables on every iteration ([docs/register-allocation.md](../register-allocation.md#worked-examples)). Within a block values stay in registers, so Forge's `-O0` code is slightly better than clang's, which also keeps every local variable in memory between statements, and never identical to it.
- An edge's arguments become stores into its target's parameter slots, often from one slot to another through ADR 0019's scratch registers. A parameter's slot is almost never its argument's, so nearly every critical edge with arguments gets a new block.
- Unreachable blocks are allocated like any other block. Nothing they use comes from outside their region, and there is no register state at a block boundary to invent for them.
- `x19`–`x28` are never written, so frame lowering saves only the frame record.
- The allocation checker tracks every register and spill slot and doesn't assume that values cross blocks in their slots, so it still applies when the greedy allocator arrives.
