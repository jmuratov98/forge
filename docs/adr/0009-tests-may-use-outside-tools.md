# Tests may use outside tools; the shipped toolchain may not

The toolchain Forge ships has no third-party dependencies, but its tests may use any tool that does the job: Python, lit, googletest, reference compilers, and fetched corpora. Building Forge without its tests needs neither Python nor network access. The no-dependencies rule exists so that users get a self-contained toolchain. Tests never reach users, and ADR 0004 already exempts them from the self-hosting rules. Writing a runner and a pattern matcher in C++ would cost real milestone time, and the only gain would be purity.

End-to-end cases are judged against **committed expectations generated by clang**, not by running clang in CI. Each case carries its expected exit code and stdout. A script regenerates them with clang, and a human reviews the diff. CI then needs no reference compiler on any host, and expectations don't drift with clang versions. The roadmap's bar, "the same exit code and stdout as clang", still holds.

## Considered options

- **Test tools must be written in a language Forge compiles** (C or C++ built by Forge's own CMake build). Rejected: it means writing a runner, a pattern matcher, and update scripts from scratch before M1, and that buys nothing the user sees.
- **Test tools must be ones whose interpreter Forge could build.** Rejected as meaningless: CPython, Tcl, Perl, and Lua are all C, so the rule excludes almost nothing.
- **Live differential testing against clang in every CI run.** Rejected for the end-to-end suite: every host, including MSVC and MinGW, would need clang. Live comparison belongs to random-program fuzzing (M5).

## Consequences

- lit is the runner for file-based tests and CTest is the runner for googletest. Details are in [docs/testing.md](../testing.md).
- Copyleft corpora (the GCC torture tests, TCC's tests, and c-testsuite's LGPL half) are fetched at test time and pinned, never vendored, so the repo stays Apache-2.0 WITH LLVM-exception.
